# OEM Windows installer: unpacking and static analysis

Research date: 2026-09-29. This records static inspection of the checked-in
`vendor/IE3.0+A3327_setup.exe`; the installer and its extracted Windows programs
were not executed.

## Sample and extraction

| Property | Result |
| --- | --- |
| File | [`vendor/IE3.0+A3327_setup.exe`](../vendor/IE3.0+A3327_setup.exe) (copied from `~/Resources/IE3.0+A3327_setup.exe`) |
| Size | 4,445,263 bytes |
| SHA-256 | `4923de8d3ebd7c99182e9b5621eca80bb300c775a87830826c0e17f60de04539` |
| Outer executable | PE32, Intel 80386, Windows GUI |
| Installer | Inno Setup 6.1.0, Unicode; Chinese and English; no password |
| Product metadata | `IE3.0 A3327`, version 1.0 |

7-Zip does not recognize this as a normal archive. `strings` exposes the Inno
Setup marker, but most payload data is compressed. `innoextract` 1.9 successfully
parsed this 6.1.0 installer even though its help text lists support only through
6.0.5; `--test` verified every packaged file checksum.

With `innoextract` installed, the repeatable, non-executing workflow is:

```sh
innoextract --info "vendor/IE3.0+A3327_setup.exe"
innoextract --list --list-sizes --list-checksums \
  "vendor/IE3.0+A3327_setup.exe"
innoextract --test "vendor/IE3.0+A3327_setup.exe"
innoextract --extract --output-dir /tmp/ie3-a3327 \
  "vendor/IE3.0+A3327_setup.exe"
```

The Linux system did not have `innoextract` installed, so version 1.9 was built
in `/tmp` from its upstream source release. The original installer is checked
in; extracted payloads and the analysis tool remain outside the repository.

## Extracted contents

The useful files for protocol research are:

| File | Finding |
| --- | --- |
| `app/MouseDriver.exe` | 32-bit Windows configuration GUI; CodeView metadata points to a missing `MouseDriver.pdb` |
| `app/hiddll.dll` | Native HID helper; exports device discovery, Feature I/O and report I/O APIs |
| `app/Data.ini` | Plain-text device identity, default profile templates and button mappings |
| `app/Data/Default.pbin`, `app/Data/profile.bin` | Identical SHA-256; structured profile store with UTF-16 profile/file labels, not a firmware image |
| `app/res/performancepage.xml` | Eight DPI slots, separate X and Y sliders, an X-Y Sync checkbox, and 125/250/500/1000 polling-rate choices |
| `app/res/lightpage.xml`, `app/res/Language/lan.xml` | Lighting controls and user-facing effect names |

The package manifest has no `.sys` kernel driver, `.inf`, standalone sensor SROM,
or obvious firmware image/updater. `Data.bin` is eight zero bytes and `gun.bin`
is empty. This is consistent with the repository tool being a Linux userspace
hidraw configurator rather than a kernel-driver replacement. No SROM payload was
found among the extracted files.

`MouseDriver.exe` has a CodeView path ending in
`560/AP/Code(210518)/Bin/MouseDriver.pdb`, but the PDB itself is absent. This is
useful build provenance, not proof of the mouse's MCU part number.

## HID transport recovered from `hiddll.dll`

The DLL imports `HidD_SetFeature`, `HidD_GetFeature`, `HidD_GetAttributes`,
`HidP_GetCaps`, and SetupAPI discovery functions. Its exports include
`Set_HIDVIDPID`, `Open_HIDFeatureDevice`, `SetHIDFeature`, `GetHIDFeature`,
`Open_HIDReportDevice`, `WriteHIDUSB`, and `ReadHIDUSB`.

Static disassembly establishes these buffer sizes and calls:

| Helper | Windows call | Buffer length |
| --- | --- | ---: |
| `SetHIDFeature` | `HidD_SetFeature` | 9 bytes |
| `GetHIDFeature` | `HidD_GetFeature` | 9 bytes |
| `WriteHIDUSB` | overlapped `WriteFile` | 65 bytes (`0x41`) |
| `ReadHIDUSB` | overlapped `ReadFile` | 65 bytes (`0x41`) |

The Feature helpers place a zero report-ID byte before the eight-byte payload.
The report helpers transfer a zero report-ID byte plus a 64-byte report. This
independently agrees with the Linux implementation's nine-byte hidraw Feature
buffer and 65-byte hidraw output call, and with the observed 64-byte input chunks
on A22A.

## `MouseDriver.exe` control flow recovered with Ghidra

Ghidra 12.1.4 headless analysis recovered the following important functions.
The executable has no PDB, so these are image addresses and autogenerated names,
not stable source symbols.

| Image address | Recovered role |
| --- | --- |
| `00416f20` | Loads `Data.ini`, including VID/PID, `Sensor`, `DPI_X/Y`, both 128-byte attribute templates and the 80 five-field button entries |
| `00419f10` | Loads `hiddll.dll` and resolves its HID exports with `GetProcAddress` |
| `00415e90` | Apply handler: applies Windows pointer settings, sends vendor feature commands and flushes changed files |
| `0041a3b0` | Report-rate command `0x03` |
| `0041a470` | Resolution-slot select command `0x04` |
| `0041a520` | Per-file 128-byte profile writer (`0x0c`); includes sensor-dependent DPI encoding |
| `0041aed0` | Writes profile configuration (`0x0c`) including global indicator/color data |
| `0041b2b0` | Serializes sixteen button actions and writes the button block (`0x0d`) |
| `0041ba90`, `0041bce0` | Macro data paths using command `0x0f` |

The Apply path sends `0x01 0x88`, then `0x02` with the selected file index plus
one. It walks five file slots and flushes changed sections: rate (`0x03`), slot
selection (`0x04`), profile settings (`0x0c`), macros (`0x0f`), button maps
(`0x0d`), macro data (`0x0f`), and lighting/global color configuration (`0x0c`).
It sends `0x02` for the selected file again at the end. The purpose of the
`0x01 0x88` request is not established.

The `0x0c` writer builds the eight-byte host Feature payload with command `0x0c`,
a 1-based file/profile index, length `0x80`, and checksum
`(0xff - command - profile - length) & 0xff`. It then sends two 64-byte Output
reports, sleeping about 30 ms between them. The button writer uses the analogous
`0x0d` request and two chunks. The rate writer maps the four UI choices to
`08/04/02/01` (125/250/500/1000 Hz) and sends `0x03`; the slot writer sends `0x04`
with 1-based profile and slot numbers. The button writer serializes sixteen
four-byte records and pads the rest of the 128-byte block.

The top-level Windows Profile selector loads a local profile bundle; its five
File entries are the device profiles the Apply handler iterates and writes as
wire profiles 1..5. Profile 0 is handled separately for global configuration
and lighting colors. This is why the app's five File entries should not be
mistaken for a five-profile device.

These traced write routines use fixed sleeps and do not perform the Linux tool's
per-chunk readiness polling and full-block readback in the functions examined.
The Linux transaction checks should be retained rather than imitating this
weaker sequencing.

### Sensor-specific DPI encoding

The loader sets a global sensor code from `[Default] Sensor`. For `Sensor=3327`
(`0x0cff`), the performance-page setup sets the eight DPI sliders to a maximum
of 124 and labels the right end `12400`. In the profile writer, each logical
stage value `n` is converted for the X DPI table (profile-block bytes 84..91) as:

```text
n == 1       -> 0x02
2 <= n < 63  -> n
n >= 63      -> floor(n / 2) | 0x40
```

Here `n` is the UI stage value; for values above the special minimum, the UI
labels it in 100-CPI steps. For example, the code emits `0x68` for `n=80`
(8000) and `0x7e` for `n=124` (12400). The high-range branch sets bit 6 and
halves the value; it is not a modulo-64 conversion. Other sensor
IDs have different branches: for example, `Sensor=3333` (`0x0d05`) keeps
`n < 81` unchanged and encodes `n >= 81` as `floor(n/2) | 0x80`. This is strong
evidence of the OEM application's sensor-specific wire encoding, but it is
static code evidence, not a calibrated measurement of the attached mouse's
sensor response.

### Lighting modes and parameters

The Light page stores the selected option number minus one in its app model; the
profile writer copies that zero-based index directly to config byte 71. The UI
labels therefore map to these byte values:

| UI option | Label | Byte 71 |
| ---: | --- | ---: |
| 1 | Off | 0 |
| 2 | Standard | 1 |
| 3 | Twinkle | 2 |
| 4 | Breathing | 3 |
| 5 | Neon | 4 |
| 6 | Wave | 5 |
| 7 | Slide | 6 |
| 8 | Finger movement | 7 |
| 9 | Flip up and down | 8 |
| 10 | YO-YO | 9 |
| 11 | Cross flash | 10 |
| 12 | Flying star | 11 |

Only options 1-4 and 10-11 are visible in this A3327 layout. The app does not
decode mode as `byte & 3`: values 9 and 10 remain distinct effects. This
invalidates the former Linux low-two-bit decoder and its `single`/`waterflow`
labels; the current CLI uses the full zero-based enum.

The writer also creates bytes 72-73 from two per-effect parameters, rather than
copying one universal “brightness” and “speed” pair. In the recovered code the
parameter bytes are: mode indices 0/6/11 -> `00 00`; 1/2/7 -> `A 00`; 3/4 ->
`00 (0x0b-B)`; 5 -> `A B`; 8 -> `A (0x14-B)`; 9 -> `A (0x0f-B)`; 10 ->
`A (0x1e-B)`. `A` and `B` are internal per-effect settings; their complete UI
unit/range conversion and live firmware response still need verification.

For colors, the `0x0c` writer places the global indicator enable flags at
bytes 16..23 and the global eight-color table at 24..47 of profile 0. Fixed-color
mode duplicates one RGB triple into all eight entries; palette modes copy eight
RGB triples. The three UI radio choices are internally numbered 0=fixed, 1=DPI,
2=cycle. The DPI-stage color selector uses a separate per-stage path; verify its
exact UI-to-wire mapping and visual effect on hardware. Linux exposes explicit
writers for the recovered global table and the profile's eight RGB triples; it
does not change the radio choice or indicator-enable bytes because their selector
encoding is not established.

The performance-page handler at `0041d7f0` stores the X/Y slider values as
per-file model fields. The checkbox handler at `0041de40` copies X to Y when Sync is turned
on; while enabled, changing either slider mirrors that value to the other. The
profile writer at `0041a520` copies those model values into
profile-block bytes 74 and 75. This is a software-side value-copy operation, not
a device mode-bit toggle. The UI does not expose a separate Y slider for each of
the eight DPI stages; the stage list has one value per stage. The physical effect
of the scale fields and the Y-stage table at bytes 92..99 still need hardware
verification.

The main Apply handler also calls `SetDoubleClickTime` and
`SystemParametersInfoW` (including `SPI_SETMOUSE`, `SPI_SETMOUSESPEED`,
`SPI_SETWHEELSCROLLLINES`, and `SPI_SETDOUBLECLICKTIME`). These options are
Windows host settings, not all mouse HID commands.

The global color writer (`0041aed0`) constructs the profile-0 config block. It
copies eight DPI-indicator enable bytes into offsets 16..23 and writes eight RGB
triples at offsets 24..47. In fixed-color mode it repeats one RGB value for all
eight entries; otherwise it copies an eight-color palette. Linux's `led color`
commands update this table while preserving the enable bytes. The DPI-stage
writer edits one RGB triple at 104+3*(slot-1) in the active profile, based on the
known eight-entry block layout; the exact vendor UI write path is not isolated.
Neither path proves the attached mouse's visible behavior. Mode and per-effect
parameter transforms are statically recovered; hardware response and exact
slider-to-parameter conversion remain unverified.

## A22A-specific configuration evidence

`app/Data.ini` says:

```ini
[Default]
VID=04D9
PID=A22A
DPI=6
Sensor=3327
Ver_H=2
Ver_L=1
```

`Sensor=3327` is important A22A-specific OEM evidence. It conflicts with the
project's earlier PAW3333 hypothesis, which came from a different reference
device and the observed 100-CPI step. The installer field is a vendor profile
value, not a sensor die marking, so the physical part is unresolved; do not
silently relabel it PAW3327. The successful 1200/1600/3200 writes remain valid
low-range observations. The earlier claim that raw 80 definitively wraps to 16
is not established; the OEM encoder emits `0x68` for logical 8000, rather than
the plain `0x50` emitted by the pre-fix Linux `/100` writer. Linux now mirrors
the OEM write-side transform, but its inverse remains a CPI estimate.

`ATTRIBUTE_0` and `ATTRIBUTE_1` each contain eight 16-byte rows, matching the
size of the project's 128-byte configuration blocks. Their contents include
sensor/register initialization fields, DPI tables, rate/count values and color
data. `[BUTTON]` contains repeated groups of sixteen four-byte action records
plus an enable value. These are OEM defaults/templates, not a captured dump of
the connected mouse: several values differ from the recorded live baseline.
Do not write an `ATTRIBUTE_*` template to the device as a recovery or reset
image.

The extracted performance UI exposes independent X and Y sliders and an X-Y
Sync checkbox. Static disassembly ties their values to profile config bytes 74
and 75. The sync checkbox's exact state transition and the physical effect still
need device verification. The current Linux `dpi` command edits the X stage
table at 84..91 and preserves both Y stages and scale fields.

The lighting UI defines twelve names (`Off`, `Standard`, `Twinkle`, `Breathing`,
`Neon`, `Wave`, `Slide`, `Finger movement`, `Flip up and down`, `YO-YO`,
`Cross flash`, `Flying star`); modes 1-4 and 10-11 are visible in this layout.
Intensity and pulse controls include 0..255 sliders. These UI ranges and labels
are useful trace targets, but do not establish a slider-to-A/B conversion. The
Linux `led mode` command applies the statically recovered per-effect writer
transforms; visible behavior and slider conversion still need hardware capture.

## Next reverse-engineering steps

1. Capture the attached device's X-table bytes before/after values around 6200,
   6300 and 8000 DPI, then compare the physical CPI response. This will resolve
   whether its live data follows the OEM Sensor=3327 path.
2. Capture X/Y scale and sync changes and compare profile bytes 74/75.
3. Capture one lighting mode, intensity, color-radio, indicator-enable and
   per-DPI color change at a time; compare offsets and verify the visible effect.
4. Recover the remaining button-action enum from the table near `0041b2b0` and
   treat the command-0x0f macro path as a separate, high-risk protocol.
